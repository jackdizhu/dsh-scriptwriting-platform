## 3. 结构性重估（架构层，需拍板）

### 3.1 `store-local` 已不是 Provider，职责与文档描述脱节（已改名 `-store`）

存储决策（`docs/decisions/2026-11-21-存储后端与store-local定位.md:32`）确定 `store-local` 只做「声明领域 spec」，**真正的 Provider 是 harness 的 `@deepseek-ai/dsh-storage-sqlite`**。于是：

- 三角色里 Provider 这一格空了，`store-local` 变成「领域 spec 声明包」，与目录大纲里 `# Provider：本地持久化实现`（`docs/decisions/2026-11-21-项目代码目录大纲.md:54`）的说法直接矛盾；
- `rules/plugin-package.md:31` 要求「包/类命名按当前稳定职责，不用首个实现或未来扩展命名」——`store-local` 是按「首个实现（本地）」命名的，而实现已不存在。

**处理（2026-11-21 用户决定）**：包名由 `dsh-scriptwriting-store-local` 改为 **`dsh-scriptwriting-store`**，目录名 `packages/store-local` 保持不变。

- `-local` 被去掉，命名不再暗示「本地后端实现」，原先最主要的失真点消除；
- `store` 保留，仍与该包「声明领域存储 spec」的职责相符，属可接受的近似；
- 曾提议的 `dsh-scriptwriting-domains` 与 `dsh-scriptwriting-platform` 两个方案均未采用（后者会与组合包 `dsh-scriptwriting-platform` 撞名，已撤销）。

配套仍需修正的文档描述（与改名独立）：

1. `docs/decisions/2026-11-21-项目代码目录大纲.md:54` 的角色标注由「Provider：本地持久化实现」改为「领域 spec 声明（Provider 由 harness `@deepseek-ai/dsh-storage-sqlite` 担任）」；
2. `packages/store-local/README.md` 首段显式声明「本包不是 Service Provider，不实现持久化」，避免后来者按包名来这里找数据库代码；
3. `docs/dsh-plugin-development-guide.md:513` 的角色描述同样仍是「Service Provider：本地持久化实现」。

**遗留风险（接受）**：目录名仍是 `store-local`，与包名 `-store` 不完全一致；改名只动 `package.json` 的 `name` 与引用键，不动路径，属显式接受的取舍。

### 3.2 依赖方向违规：Consumer 依赖了 Provider

`packages/tools/package.json` 的 `peerDependencies` 含 `dsh-scriptwriting-store`（评审时为 `dsh-scriptwriting-store-local`）；而同一批文档三处都写了 `tools` 只能依赖 `core`：

- `rules/plugin-package.md:28`「Provider 与 Consumer 互不依赖，都只依赖 Definition」
- `docs/decisions/2026-11-21-项目代码目录大纲.md:83`「`store-local`（Provider）与 `tools`（Consumer）都只依赖 `core`，二者互不依赖」

**影响**：一旦 tools 直接 import 领域 spec，领域 spec 的任何 schema 变更都会变成 tools 的破坏性升级；未来若要接第二个存储后端，tools 得跟着改。**修法**：tools 只依赖 `core` 的领域类型 + 运行时经 `ctx.get('storageDomain')` 取句柄，不 import `store-local`。

### 3.3 水平切分 → 新增一个领域要改 5 个包

现状是「按角色切」（core / store / tools / ui）。按 `docs/dsh-plugin-development-guide.md` §5.1，一个平台功能（如世界地图）天然需要 Definition + Consumer + UI 三层，于是新增功能的改动面固定为：core 加类型 → store-local 加 spec → tools 加工具 → ui 加节点 → bundle 碰版本。6 个领域 × 4 层 ≈ 24 处改动，且每处都要重新对齐版本。

**两种可选路线**：

| 路线 | 形态 | 优点 | 代价 |
|---|---|---|---|
| A. 维持水平切分（现状） | core / store-local / tools / ui / bundle | 与手册 §5.2 一致；单包职责单一 | 每功能横跨全仓；版本对齐负担随包数增长 |
| **B. 领域垂直切分（建议）** | `core`（共享原语）+ 每领域一包（`world` 内含 spec+tools+ui 节点）+ `bundle` | 功能自洽、可独立开关与独立发版；改动面收敛到 1 包 | 与手册 §5.2 的建议形态不同，需在决策记录里显式 supersede 并说明理由 |

**推荐 B 的判据**：项目自己的拆分理由（`docs/decisions/2026-11-21-项目代码目录大纲.md:21`）是「角色需要独立演进或替换」。存储决策之后，剧本领域**不存在**需要独立替换的角色——后端已由 harness 提供，工具与 UI 也不会各自换实现。相反，真正独立演进的是**领域本身**（世界地图加字段不应该牵动人物关系）。判据指向垂直切分。

保留 `core` 是必要的：品牌类型（`SessionId` 式）、跨领域引用（人物 ↔ 时间线）、共享错误类需要一个中立落点。

## 4. 稳定性缺口

1. **schema 演进无策略**。`DomainSpec` 只有 `version` / `compatibleVersions` / `invalidRecords`（`packages/storage/storage-domain/src/spec.ts:30-73`），**没有迁移机制**；且默认行为是「任一记录不合 zod 就整个 open 失败」。剧本正文这类用户资产不能靠丢弃恢复。**建议**：决策记录写明「领域 schema 只做加法（新字段可选）、版本号单调递增、禁止收窄已有字段」；正文类大记录用 `layout: 'per-record'`，避免整篇文档重写与整域失效。
2. **`pnpm test` 空跑即绿**。根脚本 `pnpm -r --if-present test`，但无一包定义 `test`；`tests/composition.test.ts` 既不在任何 tsconfig `include` 内，也无 runner。这是最坏的一种红：CI 会报告通过。**修法**：装 vitest，`tests/` 提为 workspace 包或在根配 `vitest projects`，让 `pnpm test` 至少跑到 `0 tests` 之外的真实断言。
3. **测试位置违反自家规则**。`rules/typescript.md:14`「测试放包级 `tests/`，不放 `src/__tests__/`」。现状是根级 `tests/`，与包级约定冲突——要么改规则，要么挪进 `packages/bundle/tests/`。
4. **错误处理规范未落地**。`rules/typescript.md:31-38` 要求错误继承 `HarnessError`、`code` 用 `UPPER_SNAKE_CASE`、工具预期失败抛 `ToolArgsError`。骨架里没有任何错误类或占位，第一次写工具时极易按普通 `Error` 写下去。**建议**：在 `core` 先放一个 `ScriptwritingError extends HarnessError` 与错误码枚举。
5. **依赖双重声明不一致**。`bundle` 把四个自家包放 `dependencies`，而各包之间又互为 `peerDependencies`（如 `tools` → `core`、`store-local`）。同一实例被两条路径声明，版本漂移时会出现双实例。**建议**：自家包在 workspace 内统一 `workspace:^`，`bundle` 用 `dependencies`，包间一律 `peerDependencies` + 相同范围。
6. **`workspace:` 协议被主动放弃**。`.workbuddy/memory/2026-11-21.md` 记录「树外包用 npm semver，不用 `workspace:` 协议」，理由是参照了 harness 的**已发布** manifest。但该仓库源码实测 391 个 `package.json` 使用 `workspace:*` / `workspace:~`（如 `packages/bundle/base/package.json:143`）——发布时 pnpm 会自动改写。照抄发布态而非源码态，导致本地无法 link。**这条需要纠正**。

## 5. 自定义能力扩展缺口

1. **UI 包没有客户端入口**。`packages/ui/package.json` 无 `dsh.client`、无 `exports["./client"]`、无 browser 条件。harness 中 98 个包声明了 `dsh.client`（示例 `packages/api/gateway/package.json:40-45`：`inject` + `platform: "web"`）。**影响**：`ui` 现在只能注册服务端插件，Web Client 节点与流式展示这两件事一件也做不了；`packages/ui/src/index.ts` 的 TODO 在现有 manifest 下无法实现。
2. **bundle 不自包含**。`packages/bundle/cordis.patch.yml` 只插入一行自引用；`packages/bundle/src/index.ts:14-15` 注释称「harness 的 storage 三包由 profile 侧保证先行」。但 harness 自己的组合包是把 storage 行**写进 patch** 的（`packages/bundle/base/cordis.patch.yml:181-190`，含 `backend: json` 配置）。**影响**：用户 `dsh plugin add` 之后还要手工配 profile 才能跑，安装即失败（`form-not-mounted`）。**建议**：bundle patch 内插入 `storage` / `storage-sqlite`（`path`、`journalMode` 配置）/ `storage-domain`（`backend: sqlite`）+ 本平台各插件行，`apply()` 只留跨插件 wiring。这也正是「组合包」这个分发格式存在的意义。
3. **命令、jobs、审批三类入口无占位**。§5.1 表里 `/outline` 命令、定时生成、写操作审批都需要独立注册点，目前 5 个包里没有归属。建议在垂直切分后明确「命令入口归属 bundle 还是领域包」，避免上线时四处散落。
4. **Model Experience 只填了占位**。四个 README 的 `What the model sees` 都是 `None` 或「待填充」。工具包一旦上线就贡献 token，`rules/delivery.md:36` 把它列为交付门禁。骨架阶段可接受，但要在进入能力填充前把 `tools` 的模板改成含「schema 原文 + token 上限 + KV Cache 失效条件」的表单，否则会被跳过。

2. **`docs/1.md` 是 0 字节空文件**，且被目录大纲列为既有文档。删除或补内容。
3. **`README.md` 只有两行英文描述**，无定位、无安装、无结构图。对后期维护者（含下一个 Agent），`AGENT.md` 才是真入口，README 应与之一致并指路。
4. **`github-projects/` 联接被忽略，但缺重建说明**。`.gitignore:8` 忽略整个联接是正确的（不该提交外部仓库），代价是新克隆后联接不存在，`AGENT.md` §3 要求的「引用前先确认目录联接可用」会全线失败。**建议**：在 `README.md` 写明一条重建命令（Windows：`mklink /D`；POSIX：`ln -s`），否则第二个维护者接手时所有 `github-projects/deepseek-harness/...` 引用都是死链。

6. **日志与仓库状态曾不一致**。`.workbuddy/memory/2026-11-21.md:44-50` 记录 `.gitignore` 已创建并验证，但评审开始时的实际文件列表里没有它（11:04 才出现，时间戳与日志描述一致，属并行会话产物）。此类漂移会让下一个 Agent 误信日志已完成某项工作。**建议**：日志条目附 commit 号或「未提交」标记，且不把「已验证」写成结论而不留命令输出。
