# docs 索引与写作规则

本目录是项目的**结论层**：现状、决策、评审、计划。过程记录在 `.workbuddy/memory/`，不在此处。

## 目录分区

| 路径 | 内容 | 时间语义 | 谁改 |
|---|---|---|---|
| `architecture.md` | 系统当前结构：运行时、包、数据、构建、装配 | **现在时**，随代码演进 | 每次架构变化同步更新 |
| `decisions/` | 一决策一文件，含取舍与理由 | **过去时**，写完冻结 | 只新增，只加 superseded 标记 |
| `reviews/` | 一次性评审快照（现状评级、问题清单） | 时间切片，不更新 | 不再改动 |
| `plans/` | 分阶段执行计划：阶段划分、退出条件、验收清单 | **未来时**，随推进更新 | 阶段完成即回写状态 |
| `dsh-plugin-development-guide.md` | 操作手册：环境、流程、代码模板、常见坑 | 现在时 | 流程变化时更新 |

## 写入门槛

新建文件前先过这四问，**大多数情况不该新建文件**：

| 你要记录的内容 | 去处 | 新建文件？ |
|---|---|---|
| 有 ≥2 个可行选项、需要用户拍板 | `decisions/` | ✅ |
| 跨多个阶段、有明确退出条件的执行序列 | `plans/` | ✅（每阶段一份，完成后归档或并入下一版） |
| 只是当前结构 / 现状 | `architecture.md` 对应章节 | ❌ |
| 试错过程、命令输出、临时结论 | `.workbuddy/memory/<日期>.md` | ❌ |
| 操作步骤、代码模板、常见坑 | `dsh-plugin-development-guide.md` | ❌ |
| 行为约束（必须/禁止） | `rules/` | ❌ |

补充判据：只有「包边界、公共 API、数据 schema、发布形态、扩展点归属」这类**不可轻易回退**的选择才值得一份决策记录。命名细节、内部实现取舍写进 `architecture.md` 或 commit message 即可。

## 文件规范

- 命名：`YYYY-MM-DD-<主题>.md`，主题用中文短语，日期为**决策拍板日**。
- 头字段固定四项：`状态` / `日期` / `关联功能` / `关联决策`（评审记录用 `类型` 替代 `状态`）。
- 状态机：`proposed → accepted → superseded`。被替代时**不改正文**，只在头部加 `superseded-by: <相对路径>`；旧记录继续保留，供追溯。
- 体量：单份 ≤ 150 行。超过说明主题不单一，应拆分或改为写进 `architecture.md`。
- 归档：`superseded` 且超过 90 天的记录移入 `decisions/archive/`，索引表中标 `archived`。
- 路径：全部使用相对路径，不写机器本地绝对路径（`AGENT.md` §3）。

## 与工作日志的分工

| | `docs/` | `.workbuddy/memory/` |
|---|---|---|
| 内容 | 结论、理由、约束 | 过程、命令、试错、临时判断 |
| 读者 | 任何人（含未来的 Agent） | 本机 Agent |
| 生命周期 | 长期，随版本演进 | 日志 30 天后蒸馏进 `MEMORY.md` |
| 是否入库 | 是 | 否（已 gitignore） |

同一条内容不要两边都写：进入 `docs/` 的结论，日志里只留一句引用。

## 维护动作（每月一次）

1. 扫描 `superseded` 记录，超期移入 `archive/`；
2. 合并主题重复的记录，被合并者标 `superseded`；
3. 校对 `architecture.md` 与代码是否一致（重点：包名、命令、扩展点）；
4. 更新本页索引表——**新文件未登记视为未完成**。
