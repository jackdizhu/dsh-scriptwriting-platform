# 多作品数据模型：作品注册表 + 每作品一域（D4-BC）

- 状态：accepted（2026-11-21 用户拍板）
- 日期：2026-11-21
- 关联功能：阶段 2 `core` 类型、阶段 3 `store` spec、阶段 4 `tools`、阶段 5 真实数据接 UI；阶段 1 UI 需补作品入口
- 关联决策：`docs/decisions/2026-11-21-UI入口与承载位置.md`（D1）、`docs/decisions/2026-11-21-静态数据来源.md`（D3）

## 背景

用户明确需求：创作平台要支持**多个作品**的创作，阶段 1 的面板只能看/处理一个作品。核对现状后发现「单作品」不是 UI 局部问题，而是三层共同假设：

1. **UI**：`PANEL_ID='scriptwriting'` 单例，三个 tab kind 固定，mock 数据写死一份「晨雾港」；
2. **架构 §4.4**：领域划分候选（草稿/大纲/世界地图/人物关系/时间线/物体）全部是**领域维度**，没有「作品」作为聚合根；
3. **实施计划**：阶段 2–7 没有作品生命周期（新建/切换/重命名/删除/列表）这一步。

若按原计划先做阶段 2 领域类型，到阶段 5 真实数据接 UI 时才发现「作品数据放哪」将触发返工，违反排期原则「最小跑通优先、一次到位」。

## 选项与取舍

| 选项 | 数据布局 | 优点 | 代价 |
|---|---|---|---|
| A. 共享域 + `workId` 列 | 一套 spec，所有 table 的 key 用 `workId` 复合或每行带 `work_id` | 切换零成本、实现最简 | 隔离靠纪律（漏过滤即串数据）；删作品要逐表清；作品列表无处存 |
| B. 每作品一个 domain | 作品 = 领域实例 `sw_<id>`，各自一套 tables | 天然隔离；删/导出以 unit 为单位；工具 API 不带 workId | 切换需 close + open（有 `loadAll` 开销）；name 受 `UNIT_NAME_RE` 约束 |
| **C. 作品注册表 + 外键（入选，与 B 结合）** | `works` 域存作品元数据，数据域以 `work_id` 关联 | 作品是一等公民；列表/重命名/排序集中管理 | 共享数据域时仍有隔离纪律问题 |
| 仅改 UI 层 | 阶段 1 加多份 mock，数据模型不动 | 最快看到效果 | 阶段 5 接真实数据必然返工（已排除） |

## 结论

采用 **B + C 结合**：作品注册表域管元数据，每个作品一个独立 domain 装其内容。

1. **作品注册表域**：DomainSpec name `scriptwriting_works`，table `works`（`per-record` layout），记录 `{ id, title, createdAt, updatedAt, order }`；领域 `global` 存 `activeWorkId`。作品列表、新建、重命名、排序、删除都落此域。
2. **每作品内容域**：同一份 DomainSpec **模板**，按作品动态构造 name `sw_<id>`（`<id>` 用 `[a-z0-9_]*`，满足 `UNIT_NAME_RE = /^[a-z][a-z0-9_]*$/`，且同名只能 `open()` 一次）；域内 tables 覆盖地点/路线/人物/关系/事件，后续加大纲/草稿。
3. **切换语义**：`close(旧域)` → `open(新域)` → 更新 `activeWorkId`。切换只换数据，**右栏 tab kind 保持固定**（真源 `ui-sidebar-right/src/client/tab-registry.ts` 的 `register()` 只返回 disposer，无运行时 unregister 命令）。
4. **隔离边界**：作品间数据物理隔离在不同 unit，不需要在每个查询里过滤 `work_id`；工具侧 API 不带作品参数，当前句柄即当前作品。
5. **领域 spec 粒度**：单作品域内用**一个 spec 多 tables**（跨表引用在同一写入链内一致），对应架构 §11.2 第 3 项在此场景下取「多 tables」分支——但该项仍待独立拍板，本决策不为它背书。

**遗留待确认（不属本决策，不得据此擅自实现）**：

- 「当前作品」状态在 Node 半与浏览器半如何同步（候选：`ctx` 服务 + `dsh-client-store` 桥接，或事件驱动），需另出一份决策记录；
- 作品删除时内容域 unit 的清理时机与回收策略（同步删 / 延迟删 / 软删）；
- 作品数上限与同时打开的 domain 数（是否只保留一个活跃句柄）。
