- 关联功能：阶段 2 `core`（服务键）、阶段 3 `store`（软删字段）、阶段 4 `tools`（作品管理 API）、阶段 5 真实数据接 UI

## 背景

D4 定了「作品注册表 + 每作品一域」的数据模型，但明确留下三项运行时约束待拍板。用户本轮逐项拍板，本记录把这三项固化；D4 正文不改（过去时冻结），其「遗留待确认」段由本记录 closure。

## 决策 1：当前作品状态跨端同步 = Node `ctx` 服务提供 API，浏览器只作展示

**权威状态只在 Node 半**：注册表域 `scriptwriting_works` 的 `global.activeWorkId` 是「当前作品」唯一真值，作品列表与内容域句柄也都在 Node 侧。浏览器半**不持有、不缓存权威状态，不直接写 domain**，只通过 Node `ctx` 服务暴露的 API 查询与下达命令。这是单向数据流（Node 权威 → 浏览器投影），排除 `dsh-client-store` 双向桥接与浏览器事件驱动写回两种候选。

**API 形态**：Node 半 `apply()` 内 `ctx.provide('scriptwritingWorks', service)`，service 类带 `@Remote` 装饰器暴露 RPC，方法覆盖：

| 类别 | API | 语义 |
|---|---|---|
| 查询 | `listWorks()` / `getActiveWork()` / `getView(kind)` | 返回作品元数据、当前作品、三视图数据；浏览器只读渲染 |
| 命令 | `createWork` / `switchWork` / `renameWork` / `deleteWork` | Node 侧执行 `close`/`open`/更新 `activeWorkId`/软删，返回新状态 |
| 变更通知 | 写后 `domain/changed` → 可选 Remote stream 推失效信号 | 浏览器收到后**重新查询**，不接收状态本体 |

**同步使用场景（用户要求说明）**：

1. **打开/刷新面板**：浏览器调 `getActiveWork()` + `getView(kind)`，拿到当前作品与三视图数据快照后渲染；断线或服务缺失时降级为空态，不崩溃。
2. **切换作品**：用户在作品选择器点选 → 浏览器调 `switchWork(id)`（**不自行 close/open**）→ Node 侧执行 `close(旧域)` → `open(新域)` → 更新 `activeWorkId` → 返回新作品快照 → 浏览器用它重渲染三视图。切换只换数据，右栏 tab kind 不变。
3. **模型创作写入**：模型经 `tools` 写当前作品的地点/人物/事件 → 写在 Node 侧 `sw_<id>` 域完成 → 若有活跃观察，Node 推一条失效信号 → 浏览器**重新查询** `getView(kind)` 刷新，而不是在浏览器侧改状态或重放写入。
4. **作品管理**：新建/重命名/删除都走对应命令 API，浏览器发命令、展示返回结果；删除按决策 2 软删。

上述四场景里浏览器始终是「发命令 + 查状态 + 渲染」，无任何一步在浏览器写权威状态——这就是「浏览器只作为 Web 端展示」的落点。

**真源依据（可行性与形态，非凭记忆）**：

- `api/gateway/src/index.ts:378-388`：`collectSrcClaims()` 遍历 `ctx.reflect.props` 中 `type === 'service'` 且带 `typertRemote` binding 的对象，按 namespace 收集端点——**树外插件 `ctx.provide` + `@Remote` 即被自动发现，无需改 harness**；
- `api/gateway/src/index.ts:329-334`：`registerRemoteEvents` 支持服务端事件转发（变更通知能力存在）；
- `api/job-controller/src/index.ts:78,93,112`：`@Remote({ mode: 'stream' })` 与 `@Remote('kill')` 的既有写法（stream 查询 + 命令直传）；
- `api/job-controller/src/client/service.ts`：`ClientRemote` face + `declare module '@deepseek-ai/cordis'` 把 client service 注入 `ctx`，是「浏览器通过服务调 RPC」的参照；

## 决策 2：作品删除 = 软删

删除作品时**不清空/不销毁**内容域 unit 的数据，只在 `works` 记录标记删除状态（加 `deletedAt?: number` 字段，`null`/缺失表示有效），并从默认作品列表中过滤。作品元数据与 `sw_<id>` 数据保留，供未来恢复或导出。

- 与领域 spec「只加不改、版本单调」演进策略一致（加字段而非删记录）；
- 与决策 3 的 `close()` 语义区分：切换作品会 close 旧域句柄（释放运行时占用），软删**不删除数据**——两者正交；
- 待定（不在本记录）：回收站/彻底删除/导出的触发时机与权限。

## 决策 3：同时打开的 domain 数上限 = 1

任意时刻**最多一个内容域 `sw_<id>` 处于 open 状态**（即当前作品域）；注册表域 `scriptwriting_works` 是常驻单例元域，不计入此上限。

- 切换作品严格执行 `close(旧域)` → `open(新域)` → 更新 `activeWorkId`，与 D4 结论及架构 §4.6「同一 `ctx.effect` 串行 disposer」一致；
- `open()` 前若已有活跃内容域，必须先 `close()`，不得同时持有两个句柄；
- 上限 1 让「当前句柄即当前作品」成立，工具 API 无需带作品 id（D4 结论 4 的前提）。
