## 背景

`dsh-scriptwriting-platform` 需要一份代码目录大纲，作为后续「最小骨架跑通 → 能力填充」的落点。项目定位是**树外插件 + bundle**（`AGENT.md` §1、`docs/dsh-plugin-development-guide.md` §0.2），不是往 Harness monorepo 加包，因此目录必须遵循 bundle 的 manifest 约定，且不能照抄 workspace 包不变式。

工作节奏遵循「先确认后执行、每轮一个决策」（`AGENT.md` §6、`rules/agent-workflow.md` §1）：本轮先给方案，收到放行后才创建骨架、且不写业务代码。

## 选项与取舍

包粒度决定目录形态，是本轮唯一拍板的决策；其余决策留到对应阶段。

| 选项 | 目录形态 | 优点 | 代价 |
|---|---|---|---|
| A. 单包 + 内部模块化分层 | 一个 `dsh.bundle` 包，`src/{domain,store,tools,ui}` 内部分层 | 契合「最小骨架跑通优先」；无多包发布/版本对齐成本 | 模块间靠目录约定隔离，非物理包边界；单包体积随能力增长 |
| **B. 多包 + pnpm workspace（已选）** | `packages/{core,store-local,tools,ui,bundle}` 五个独立包 | 三角色物理隔离，可独立发布/复用 | 与手册 §5.2 的「先避免过度拆分」相悖；版本/依赖对齐负担 |

判据引用：`rules/plugin-package.md` §3「只有角色需要独立演进或替换时才拆成不同包；简单工具插件保持单包，避免预防性拆分」；`docs/dsh-plugin-development-guide.md` §5.2「若存储后端确定只有一种，可先合并 Definition + Provider，避免过度拆分」。

## 结论

**采用选项 B**：`pnpm workspace` 管理五个独立包。用户明确拍板，接受「三角色物理隔离、可独立演进」的收益，同时接受版本/依赖对齐与提前拆包的代价。放弃单包方案的内部模块化目录。

> 风险提示（不阻塞）：`core` 与 `store-local` 在存储后端未定前已拆成 Definition + Provider 两包。若后续确认只有一种本地后端，可按 `rules/agent-workflow.md` §3 用新决策记录 `supersede` 本条并合并，避免固化过度拆分。

## 包边界与依赖方向（依据 `rules/plugin-package.md` §3）

- `core` 持有 Request/Result 类型与 ctx 键声明，不依赖任何具体实现包。
- `store-local`（领域 spec 声明，**不是** Provider）与 `tools`（Consumer）都只依赖 `core`，二者互不依赖。
- `ui` 独立挂 Web Client 扩展点，依赖 `core` 的类型。
- `bundle` 只做装配，声明对其他四包的 `peerDependencies` + `devDependencies`（相同范围，`rules/plugin-package.md` §6）；不放业务逻辑。
- 跨包引用用包名，不写相对路径（`rules/typescript.md` §1）。
