# AI Agent 开发规范

## 1. 执行节奏：先确认，后执行

- 每个阶段先产出**方案 / 对照表 / 拆分清单**，收到明确放行后再进入下一阶段。
- 未经确认，不得直接写业务代码或改动既有文件结构。
- 复杂任务按阶段推进：功能→扩展点映射 → 插件拆分 → 最小骨架跑通 → 能力填充 → 验证交付。
- 遇到需求歧义先提问，不用假设填补；若必须假设，明确写出并标注为假设。

## 2. 证据驱动

- 结论必须引用具体文件路径、行号、命令输出或 commit；禁止"我认为""通常是"。
- 判读 diff 前先读需求（规则页、 owning 文档），再对照代码；不要凭对规则的记忆评审（`dsh-code-review` 原则）。
- 报告只列出**实际运行过的命令**及其结果，不虚构检查、不隐瞒失败。
- 检查失败时如实报告并定位，不得绕过失败或降低门槛使其通过。

## 3. 决策记录：一决策一记录

- 每个已确认的架构决策回写本仓库 `docs/YYYY-MM-DD-<主题>.md`，模板见 `docs/dsh-plugin-development-guide.md` 第 8 节。
- 状态机：`proposed → accepted → superseded`；记录背景、选项取舍、结论、依据、验证方式。
- 标注建议 vs 已确认：未放行的映射一律写"设计建议（待确认）"，不得写成事实。
- 设计理由放决策记录，不放代码注释或正文文档；历史只留在记录与 commit 中。

## 4. git 权限分级（强制）

| 操作 | 权限 |
|---|---|
| `status` / `add` / `diff` / `log` / `commit` / 本地 `reset`（非 `--hard`） | AI Agent 可直接执行 |
| `push` 及任何远程仓库写入（含 force push） | **禁止** AI 执行，由用户手动 |
| `fetch` / `clone` / `pull` 等远程读取 | **禁止** AI 执行，由用户手动 |

- AI 可读取 `.git` 目录内的纯文件（HEAD、packed-refs、config）做诊断，但不得调用 git 可执行程序执行上述禁止操作。
- 提交前执行 `git diff --cached --check`；文件末尾必须恰好一个换行。

## 5. 检查纪律（来自 Harness 根规范）

- 只运行与改动表面相关的检查；**不要**默认跑全量套件，也不要重复已通过的检查。
- 证据要匹配表面：行为改动跑聚焦测试，模型/用户输出改动跑快照，文档改动跑 `doc-sync`，发布路径跑构建烟测，provider 改动跑真实 API e2e。
- 需要沙箱提权时，先留 sandbox 证据，再用最小范围提权；永不绕过测试失败或产品沙箱。
- CI 负责穷举覆盖与平台矩阵；本地全量仅在明确要求、CI 诊断或确实仓库级改动时执行。
- 文档改动需同时更新受影响的 README 与 JSDoc；`dsh-translate-docs` 仅在用户显式要求时运行。

## 6. 评审与报告

- 发现缺陷写清：缺陷、位置、影响、证据；区分 blocker 与 suggestion。
- 收到评审意见时逐条技术核验，以事实回应，不做表演性认同。
- 测试描述行为而非正确性；废弃行为随测试一起改，并在 PR 中解释原因。

## 7. 与规则的关系

本文件约束"怎么做"，`typescript.md` 约束"写成什么样"，`plugin-package.md` 约束"插件怎么组织"，`privacy-security.md` 约束"什么不能做"。规则冲突时以隐私安全与事实来源优先级为准。
